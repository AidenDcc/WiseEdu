## 一、目标与范围

1. 以 `schema.sql`（140 张表 / 12 个数据域）为**逻辑数据模型权威**，在其之上落地一套可持续演进的后端。
2. 采用「单体优先、可平滑拆微服务」的 JeecgBoot 架构，教学云业务代码独立成模块，通过网关按前缀灰度接入。
3. 迁移策略：**从管理端（超级管理端）开始**，把管理端的 Mock 服务逐步迁移到真实后端，机构端随后跟进。
4. 全程遵守仓库既有工程约定（`edu_` 前缀、租户行级隔离、`del_flag` 逻辑删除、统一响应、`org_tenant_id` 外键命名）。

### 分层规范（每个业务模块内部）

```text
org.jeecg.modules.edu.<端>.<域>
  ├── controller/      # REST 控制器（路径照抄前端 apps/*/src/api/*.ts，自带 /admin 或 /tenant 前缀）
  ├── entity/          # MyBatis-Plus 实体（@TableName / @TableId）
  ├── mapper/          # BaseMapper 接口 + mapper/xml/ 下的手写 SQL
  ├── service/         # I<Entity>Service 接口
  │   └── impl/        # <Entity>ServiceImpl 实现
  └── vo/              # 请求/响应对象（对齐前端 @aiteach/shared 数据契约）
```

统一响应：`ApiResult<T>`（`code=0` 成功，`message`，`data`）；业务错误用 `ApiResult.fail(code, msg)`。

## 三、数据模型映射（schema.sql → JeecgBoot 物理表）

`schema.sql` 用 `sys_ / dc_ / q_ / p_ / t_ / r_ / e_ / ai_ / c_ / g_` 前缀定义 140 张表，其中 **`sys_*` 与 JeecgBoot 框架表重名且结构不同**（如 `sys_user`、`sys_role`、`sys_menu`、`sys_tenant`、`sys_dict_item`）。两者必须和解，否则框架鉴权/RBAC/菜单/字典会被业务 DDL 摧毁。

### 3.1 和解原则（三级）

| 类型 | 处理方式 | 示例 |
|------|---------|------|
| **A. 框架自有表（不改）** | JeecgBoot 的 `sys_user/sys_role/sys_permission/sys_menu/sys_dict/sys_dict_item/sys_log/sys_tenant/sys_announcement/sys_category/sys_depart/sys_quartz_*` 原样保留，承载鉴权、RBAC、菜单、字典、日志、定时任务 | `sys_user`、`sys_role` |
| **B. 业务扩展表（edu_ 前缀，1:1 或 1:N 挂框架表）** | schema.sql 中「比框架表更丰富」的 `sys_*` 业务表，落地为 `edu_*`，外键指框架表 | `sys_tenant`(框架) + `edu_tenant_ext`(扩展) |
| **C. 纯业务表（按域落 edu_ 前缀，物理名沿用 schema.sql 词根）** | `dc_/q_/p_/t_/r_/e_/ai_/c_/g_` 前缀表与框架无冲突，映射为 `edu_<词根>`，字段一一对应 schema.sql | `q_question` → `edu_question` |

> **命名硬规则**（沿用仓库约定，不可违反）：
> 1. 业务表一律 `edu_` 前缀；机构端业务表必须带 `tenant_id int NOT NULL DEFAULT 0` 并建索引（`TenantLineInnerInterceptor` 行级隔离列）。
> 2. 「引用某个租户」的外键列一律命名 `org_tenant_id`，**绝不能叫 `tenant_id`**（会被租户拦截器静默改写）。
> 3. 平台侧全局共享表（套餐、租户扩展、入驻申请、字典扩展等）**不登记进 `TENANT_TABLE`**，不做行级隔离。
> 4. 主键：前端 `id` 为 `number` 的业务实体用 `bigint AUTO_INCREMENT`（避免雪花串超出 JS `Number.MAX_SAFE_INTEGER`）；前端 `id` 为 `string`（如 `sys_user.id`）的保留 `varchar(36)` 雪花串。

## 四、关键工程约定

### 4.1 ID 策略

| 场景 | 类型 | 理由 |
|------|------|------|
| 前端 `id` 为 `number` 的业务实体 | `bigint AUTO_INCREMENT` | 雪花 19 位超出 JS `Number.MAX_SAFE_INTEGER`，静默丢精度（`edu_question_category` 已确立该样板） |
| 框架 `sys_user.id` 等 | `varchar(36)` 雪花串 | 前端统一按 `UserId = string \| number` 处理，`String()` 归一化后再比较 |
| `sys_tenant.id` | `Integer`（框架既定） | 存量为 1000/1001 小整数，与前端 `number` 天然对齐 |

### 4.2 租户隔离

- 机构端业务表带 `tenant_id`，写入由 `MybatisInterceptor` 自动填当前登录租户，查询由 `TenantLineInnerInterceptor` 自动追加 `tenant_id=?`；业务代码**不手工赋值**。
- 平台侧共享表（套餐/租户扩展/入驻申请/字典扩展/内容运营/AI 计费等）不进 `TENANT_TABLE`。
- 登录租户由 `system.setLoginTenant()` 从 `sys_user_tenant` 里挑，写回 `sys_user.login_tenant_id`；**后续每个请求都按这个值还原租户上下文**。所以「只在内存里改登录租户」是无效的，必须落库（见 6.3）。
- 平台超管（持框架 `admin`/`superadmin` 角色）恒为租户 `0`，不参与租户隔离（见 6.3）。

### 4.3 删除三态与回收站

- 需求文档把 `deleted` 定为三态（0 未删 / 1 回收站 / 2 彻底删除）。JeecgBoot 现用 `del_flag`(0/1) + `@TableLogic`。
- **落地策略**：业务表保留 `del_flag`（0/1）承接「进回收站」软删；「恢复 / 彻底删除」由 `edu_recycle_bin` 表承载三态（`bin_status` 0 已恢复 / 1 回收站 / 2 已彻底删除），对账逻辑在回收站服务里。彻底删除走物理删除 + 回收站终态标记。

### 4.4 统一响应

- 教学云业务接口统一 `{ code, message, data }`，`code=0` 成功（`ApiResult`）。
- 框架鉴权/全局异常返回 `{ success, code, message, result }`；请求层两种都认。
- 鉴权头 `X-Access-Token`（非 `Authorization: Bearer`），租户上下文 `X-Tenant-Id`。

### 6.0 单库接管方案（当前生效）

#### 为什么改

原方案是「`jeecg-boot` 框架库 + Flyway 增量建 `edu_*` 表」，结果业务表散落成 `edu_tenant_ext` 之类的过渡表，
与 `schema.sql` 定义的 `sys_tenant` 主模型长期双轨并存，数据要写两份、查询要 JOIN、字段语义还要翻译。

### 6.3 登录链路：口令哈希与租户上下文（v1.4）

切到真实后端后第一个暴露的问题是「**账号密码都对，却提示账号或密码错误**」。根因不在校验逻辑，而在两侧的哈希口径完全不同：

| | 前端 Mock | 后端 jeecg |
|---|---|---|
| 算法 | `sha256(salt + password)` | `PBEWithMD5AndDES`（PBKDF1-MD5，1000 次迭代） |
| 凭据存哪 | `packages/shared/src/auth/accounts.ts`（随 bundle 下发） | `sys_user.password` + `sys_user.salt` |

Mock 时代 `admin / admin0123` 走的是前者；库里 `admin` 的哈希其实是 jeecg 默认口令 `123456`，
所以换成后端校验必然失败。另有 16 个演示账号 `password` 直接为 `NULL`（`seed_mock.py` 只写业务字段、不编口令），
连登录入口都进不去。

**算法口径（`PasswordUtil.encrypt(username, password, salt)`，参数语义极易搞反）**：

```
明文   = username        ← 加密的是账号，不是密码
PBE 口令 = password
盐     = sys_user.salt（8 字符，直接拼在口令后做 PBKDF1，无额外内部盐）
输出   = DES/CBC/PKCS5Padding 密文的十六进制小写
```

`db/jeecg_pwd.py` 是这套算法的纯 Python 实现（机器上没有 pycryptodome/cryptography，
不想让「一键重建」变成「先装依赖」），自带两条自检向量：
DES 标准向量 `133457799BBCDFF1/0123456789ABCDEF → 85e813540f0ab405`，
jeecg 向量 `admin/123456/RCGTeGiH → cb362cfeefbf3d8d`。自检不过直接抛异常，不让错误静默。

`db/07_demo_passwords.py` 按账号逐条重算并写库（幂等：盐保持原值，无盐则按账号名派生固定盐，
所以 `--dry-run` 的输出可以当变更单核对）。保留 `jeecg` / `zhangsan` / `ceshi` 三个框架自带账号的原口令，
其余统一 `admin0123`。一键脚本第 9 步调用它。

**顺带修掉的两处「语义冲突」**（与 v1.2 的 `sys_user.status` 同一类问题）：

1. **`sys_tenant.status` 四值被框架当二值**。业务定的是 `1 试用 / 2 正式 / 3 已到期 / 4 已禁用`，
   框架 `SysUserTenantMapper.xml` 里四处「租户可用」判定都写死 `status = 1`，
   于是**全部「正式」租户被判成不可用** —— 表现是登录成功但 `loginTenantId = 0`、机构端拿不到数据。
   四处统一改为 `status in (1, 2)`（试用与正式均可用，到期/禁用不可用）。
2. **平台超管被塞进演示租户上下文**。框架会给 `admin` 从 `sys_user_tenant` 里挑一个关联租户当登录租户
   （它是 jeecg 演示租户 1000「北京国炬」）。一旦被选上，平台端所有查询就被按租户隔离，只剩那家机构的数据。
   现在 `EduAuthController` 对持 `admin`/`superadmin` 角色的账号直接置 `loginTenantId = 0`，

学生名单导入文件、导出文件 —— 全部落 OSS，本地磁盘不再保存业务文件。

**桶信息（已开通）**

| 项 | 值 |
|---|---|
| 桶名 | `aiden-dcc` |
| 地域 | 华南3（广州） |

| 自定义域名 | `aiden-dcc.cn-guangzhou.taihangztn.cn`（已 CNAME，未开加速） |
| 存储类型 | 标准存储 |

**为什么不能沿用框架的「上传即返回直链」**
JeecgBoot 的 `OssBootUtil.upload()` 返回 `https://{bucket}.{endpoint}/{key}`，前提是桶公共读、
或者代码里把桶 ACL 改成 `PublicRead`。本项目的桶是私有的，直链必然 403。三条路里选了第三条：

| 方案 | 否决理由 |
|---|---|
| 把桶改公共读 | 教学文件含学生姓名、成绩单，公读等于全网可枚举下载 |
| 返回预签名直链 | 有有效期（最长 7 天），写进业务库会过期；且暴露桶名与地域，换桶即全量失效 |
| **后端签名代理（采用）** | 地址长期有效、不暴露 AK/SK、可统一加安全响应头、换桶/换 CDN 只改配置 |

**地址形态**

```
上传返回： /api/sys/edu-file/view?key=edu/avatar/2026/10/21/<uuid>.png&sign=<hmac32>
```

- `sign = HMAC-SHA256(signSecret, key[+exp])` 截 32 位 hex，客户端改一个字符即 403；
- `key` 是 `edu/{biz}/{yyyy}/{MM}/{dd}/{uuid}{ext}`，UUID 路径不可枚举 —— 等价于
  「拿到链接就能看，猜不到就看不到」，与主流对象存储的预签名模型一致；
- 需要**临时**链接（导出、分享给外部）时用 `/sys/edu-file/sign?key=..&expireSeconds=86400`，
  或 `/sys/edu-file/view?key=..&exp=..&sign=..`。

**代码落点**

| 层 | 类 | 职责 |
|---|---|---|
| 配置 | `OssStorageProperties`（`edu.oss.*`） | 端点/桶/凭据/前缀/签名密钥/大小上限 |
| 存储 | `OssStorageService` | 上传、开流（含 Range）、删除、存在性、地址生成、Key 反解 |
| 签名 | `OssUrlSigner` | HMAC 生成与恒定时间校验；框架与业务两侧共用 |
| 框架适配 | `OssBootUtil` | 存在 `OssStorageService` 时全部委托；`/sys/common/upload` 也随之走 OSS |
| 业务门面 | `IEduOssFileService` + Impl | 准入校验 + 落库 + 回收（桶先写、库后写，库失败删对象） |
| 接口 | `EduFileController` | `POST /upload`、`GET /view`、`GET /download`、`GET /sign`、`POST /delete` |
| 准入 | `EduUploadPolicy` | 扩展名白名单 + 业务分类收窄 + 危险文件头 |
| 元数据 | `edu_oss_file`（Flyway `V3.9.6_7`） | 可追溯 / 可回收 / 可统计 / 可去重 |
| 前端 | `packages/shared/src/upload` | `uploadFile/uploadImage/uploadAvatar` + `resolveFileUrl` |

**为什么不把 URL 存进业务表**
全站约定：业务表存 `storage_key`，渲染前由 `resolveUrl()` 现算地址。只有历史字段
（如 `edu_user_profile.avatar` 是字符串列）会存地址，因此它的值也只存代理地址、不存直链。

**分片上传**
当前是 OSS 简单上传，单文件上限 200MB（`spring.servlet.multipart.max-file-size`
与 `edu.oss.max-size-mb` 同步放大到 200MB —— 框架默认 10MB 会在进 Controller 前就被
Tomcat 拒掉，前端只看到 413）。超过 200MB 的课时视频应改走分片上传（`InitiateMultipartUpload`），
本轮未做。

## 八、实施踩坑记录

1. **`Map.of().get(null)` 会抛 NPE**：`Map.of()` 返回的不可变 Map 不允许 null key，`get(null)` 直接 `NullPointerException`（不是返回 null）。任何「可选筛选条件」查 Map 前必须先判空。Wave 2 在 `listApplies` 的 status 中文→整数换算处踩到，已修复。
2. **JDBC 时间类型是 `LocalDateTime` 而非 `Timestamp`**：`mysql-connector-java 8.0.27` 的 `ResultSet.getObject()` 对 DATETIME 返回 `java.time.LocalDateTime`（已用独立 JDBC 测试实证），不是 `java.util.Date`。凡是用 `map` resultType 直查时间列、再 `instanceof Date` 判断的地方，时间字段会整页变 null。统一收敛到 `TenantJson.toDate(Object)`（兼容 Date / LocalDateTime / 字符串），禁止再散写 `instanceof Date`。
3. **打包必须 `clean package`**：只 `mvn package`（无 clean）时，`spring-boot:repackage` 不会重新生成 fat jar，改的 class 进不了 jar（表现为 jar mtime 不变、接口仍报旧错误）。改后端代码后务必 `mvn clean package -DskipTests`；增量构建可先 `mvn -pl jeecg-boot-module/jeecg-module-edu-platform install -DskipTests` 再在 system-start 目录 `clean package`。
4. **后端端口与 context-path 走启动参数，不改 yml**：`application-dev.yml` 保持框架默认（`8080` + `/jeecg-boot`），本地起服务统一加 `--server.port=9999 --server.servlet.context-path=/`（`start-dev.command` 已内置）。原因：两个前端的 vite proxy 都把 `/api` 剥离后转发到 9999，保留 `/jeecg-boot` 会 404。56641 被 WorkBuddy 桌面 Electron 占用，勿用。

### 8.1 数据库重建期踩坑（单库接管）

5. **`schema.sql` 自身有 3 处重复列**：`sys_tenant_subscription` / `sys_tenant_config` / `sys_tenant_menu` 的 `tenant_id` 被公共字段和手写字段各定义一次，直接执行报 `ERROR 1060 Duplicate column name 'tenant_id'`。已用脚本删重复行，原件备份 `doc/schema.sql.bak`。
6. **`mysqldump` 表清单必须走 `xargs`**：`mysqldump db t1 t2 ...` 里把整串表名当一个变量传，会被当成单个参数报 `Argument 'aigc_word_template airag_app ...'`。
7. **框架主键不一定是数字**：`sys_user.id` 存在 UUID 形态（`admin` = `e9ca23d68d884d4ebb19d07889727dae`），所以合并表 id 类列统一 `VARCHAR(32)`，不能用 BIGINT。
8. **⚠️ 清数据千万别用「纯数字 id」当判据**：曾写 `DELETE FROM sys_dict_item WHERE id REGEXP '^[0-9]+$' AND CAST(id AS UNSIGNED) >= 500000`，结果框架雪花 id 也全是数字，214 条字典被删到只剩 82 条。已从 `jeecg-boot` 用 `INSERT ... WHERE NOT EXISTS` 完整恢复，判据改为前缀匹配（`id LIKE 'DICT%'`），mock 字典 id 也改成 `DICT500000+n` 形态。
9. **合并表上的唯一键会撞车**：mock 里多个账号都叫 `admin`，且与框架内置账号同名 → `uk_username` 冲突。需要「保留字集合 + 已用集合」双去重并在末尾追加 `_2`、`_3`。
10. **不同 mock 文件的 id 区间会重叠**：`exam-seeds.EXAM_QUESTIONS` 与 `org-store.questions` 撞 `9223`，`p_paper_section` 跨试卷撞 `401`，`e_exam_answer` 的 `uk_session_student` 因 `student_id` 全为 NULL 撞车。分别用「偏移量（+50000）」「派生键（`pid*1000+si`）」「派生唯一值」解决，不要指望 mock 的 id 天然唯一。
11. **`getObject()` 对 DATETIME 返回 `LocalDateTime`**（见 8-2），跨库迁移时 `INSERT ... SELECT` 反而更安全，因为它不经过 Java 类型转换。

### 8.2 冲突表收敛期踩坑（v1.2 – v1.3）

12. **业务列名在 raw SQL 里最容易被漏掉**：`Sink.add()` 会按 `information_schema` 过滤未知列，所以 `seed_mock.py` 里的 `dict` 写法删列后自动安全；但 `Sink.raw` 里拼接的原样 SQL 不会过滤 —— `sys_tenant` 删掉 `deleted` 后，过渡表回填仍写 `WHERE t.deleted = 0`，换库名重建时报 `Unknown column`。改列名时必须同时搜 `raw` 段。
13. **沙箱会注入 `SERVER__PORT` 覆盖 `server.port`**：WorkBuddy Bash 环境里有 `SERVER__PORT=58959`，Spring 宽松绑定把它当成 `server.port`，于是 yml 写 8080、实际监听 58959，且该端口上还挂着沙箱自己的 Node 服务（响应头 `X-Powered-By: Express`，返回 `AUTH_REQUIRED`），误判成「后端 401」。启动时显式加 `--server.port=9999` 覆盖；判断服务归属先看响应头，不要只看状态码。
14. **`mvn -pl jeecg-system-start package` 不会带上兄弟模块的改动**：fat jar 内嵌的是 `~/.m2` 里的 `jeecg-system-biz-3.9.5.jar`。改了 biz 模块只 `package` start，jar 里仍是旧 biz（表现为「代码明明写了，接口 404」）。必须先在 biz 目录 `mvn install -DskipTests`，再 `clean package` start。

### 8.3 登录链路踩坑（v1.4）

15. **`PasswordUtil.encrypt` 的参数是「明文, 口令, 盐」，jeecg 传的是「账号, 密码, 盐」**：即**加密的是账号**、密码当 PBE 口令。按「加密密码」的思路去实现，算出来的哈希永远对不上（本文档第一版就踩了这个坑，用 jshell 逐字节比对才定位）。
16. **`sys_user.password` 为 `NULL` 时是 500 而不是「密码错误」**：`sysUser.getPassword().equals(...)` 直接 NPE。种子数据只写业务字段不编口令，切后端后这批账号根本进不到校验。
17. **平台超管会被框架挑走一个「关联租户」**：登录租户写回 `sys_user.login_tenant_id`，之后每个请求按它还原上下文；只在内存里改（`sysUser.setLoginTenantId(0)`）下一次请求就被拉回旧值，必须 `updateUserDepart()` 落库。
18. **`sys_tenant.status` 是业务四值，不能直接喂给框架的二值判断**：框架四处「租户可用」写死 `= 1`，把「正式(2)」全判成不可用。改 mapper 比改数据安全 —— 业务四值有 UI 语义，压成二值会丢信息（同 v1.2 的 `sys_user.status`，但那次是可压的，这次不是）。

### 8.4 对象存储接入踩坑（v1.5）

19. **框架的 OSS 实现默认「桶公共读」**：`OssBootUtil.upload()` 拼 `https://bucket.endpoint/key` 直链，有两处还显式调 `setBucketAcl(PublicRead)`。私有桶下直链 403，且这两行代码会把私有桶悄悄改成公读 —— 必须绕开（改为委托 `OssStorageService`），不能只改配置。
20. **`spring.servlet.multipart.max-file-size` 默认 10MB**：课时视频/课件包必然超。这个限制在 Tomcat 解析 multipart 时就生效，请求根本到不了 Controller，前端只看到 413，日志里也没有业务异常 —— 排查时容易误判成前端上传失败。已放大到 200MB，与 `edu.oss.max-size-mb` 同步。
21. **`<img>`/`<video>` 带不了 `X-Access-Token`**：代理读接口必须 Shiro `anon`，安全性改由 URL 里的 HMAC 签名承担。若图省事放开 anon 又不加签名，等于把私有桶变成「知道 Key 就能下载」——而 Key 是 UUID 路径，只能防枚举、防不了泄露。
22. **`OssStorageService` 放在 base-core 而不是 biz**：框架的 `OssBootUtil` 也在 base-core，只有放同一层才能让它俩共用同一个 OSS 客户端与同一套签名；放 biz 会造成「框架接口走公读直链、业务接口走私有代理」两套并存。
23. **Spring Boot 宽松绑定会把环境变量 `SERVER__PORT` 当 `server.port`**：本地 58959 端口上挂着沙箱代理，直接 `java -jar` 会被这个变量带偏到错误端口，且 curl 返回 `AUTH_REQUIRED`。启动必须显式 `--server.port=9999 --server.servlet.context-path=/`，curl 加 `--noproxy '*'`。
